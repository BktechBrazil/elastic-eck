Módulo 11

Capacity Plan

Dimensionar memória, CPU, disco e shards — e traduzir para requests/limits e autoscaling no ECK.

Quatro dimensões

🧠

Memória

Heap ≤ 50% da RAM e ≤ ~30 GB. O resto é filesystem cache.

⚙️

CPU

Ingestão, agregações, concorrência. Mede-se e ajusta.

💽

Disco

Dados + réplicas + margem. Nunca > ~85% (watermarks).

🧩

Shards

10–50 GB por shard; < ~20 shards por GB de heap.

A matemática dos shards

  • Tamanho: 10–50 GB/shard (pequeno = overhead; grande = recuperação lenta)
  • Densidade: < ~20 shards por GB de heap por nó
  • Séries temporais: rollover/ILM gera shards do tamanho certo
≈ nº de shards primários = volume diário / 40 GB.

Traduzir: requests × limits

resources:
  requests: { memory: 8Gi, cpu: "2" }
  limits:   { memory: 8Gi }   # == request (garantida)
env:
  - ES_JAVA_OPTS: -Xms4g -Xmx4g       # 50% do request
memória: request == limit (evita OOM/eviction). CPU: request sem limit evita throttling.

Disco: volumeClaimTemplates

  • Cada nó = um PVC; dimensione com ~25% de margem
  • Crescer: possível se a StorageClass tem allowVolumeExpansion
  • Reduzir: não suportado

Escalar

Vertical

Mais RAM/CPU/disco por nó (muda resources).

Horizontal

Mais nós (aumenta count). Distribui shards.

Autoscaling ECK

ElasticsearchAutoscaler por tier (min/max). Enterprise.

Medir para dimensionar

GET _cat/allocation?v          # disco por nó
GET _cat/nodes?v&h=name,heap.percent,cpu
kubectl top pods -n elastic     # visão do K8s
Stack Monitoring no Kibana dá o histórico de heap, GC, indexação e busca.

Resultado ✅

  • Regras de ouro de heap, shard e disco
  • requests/limits com memória garantida + heap 50%
  • Escala vertical, horizontal e autoscaling do ECK
