Mapping, Analyzers & Aliases

Controlar como o Elastic interpreta cada campo — a diferença entre uma busca que funciona e uma que devolve lixo.

Mapping = o esquema do índice

  • Dynamic — o Elastic adivinha o tipo (ótimo p/ começar, perigoso em produção)
  • Explicit — você define o tipo de cada campo
  • Tipos: text, keyword, long, double, date, boolean, object, nested
Campo mal inferido (CEP vira long, data vira text) quebra buscas silenciosamente.

Analyzer: texto → tokens

"O Menino Correu!"▶ char filters▶ tokenizer▶ token filters▶ [menino, correr]
  • char filter — limpa (ex.: remove HTML)
  • tokenizer — quebra em palavras
  • token filter — lowercase, stopwords, stemming
O mesmo analyzer roda na indexação e na busca → "correndo" acha "correu".

Depurar com _analyze

POST _analyze
{ "analyzer": "portuguese", "text": "Os meninos estavam correndo" }
// veja os tokens: stopwords removidas + radicais
Ferramenta indispensável: mostra exatamente o que foi indexado.

Aliases: ponteiro estável

  • Zero-downtime reindex — troca atômica de índice por trás do alias
  • Write alias / rollover — aponta para o índice "atual" (base do ILM)
  • Filtered alias — embute um filtro (ex.: produtos-ativos)
Aplicações devem apontar para alias, nunca para o nome físico do índice.

Evoluir mapping sem downtime

POST _reindex
{ "source": {"index":"catalogo"}, "dest": {"index":"catalogo-v2"} }

POST _aliases
{ "actions": [
  { "remove": { "index":"catalogo",    "alias":"produtos" } },
  { "add":    { "index":"catalogo-v2", "alias":"produtos" } }
] }
Campos existentes são imutáveis → índice novo + reindex + troca de alias.
